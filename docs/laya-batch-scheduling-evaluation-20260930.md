# Laya 批量清洗调度实测（2026-09-30）

## 测量范围

RTX 5070 Ti（16 GB），现有清洗台进程空闲但占用约 3 GB 显存。所有基准使用项目内微调的 `laya_wiki_cleaning_v1`，不调用网页或付费 API，不写正式队列。选了两组真实维基文档：从尚未批量清洗的队列后段按固定随机种子抽取 256 篇（合计 179,071 字，中位数约 260 字）；从已有人工作业的文档按长度分位取 64 篇（合计 545,330 字，中位数约 5,051 字、最长 42,303 字）。每组先预热模型，再比较同一组原文。报告中的吞吐量只代表本机和这两个样本分布。

模型原始 `predict_batch` 内部批大小在短文本 1,024 块上：8/16/32/64/128 分别约 740/1,059/1,136/994/855 块每秒；在较长的 1,024 块上，16 最快，约 865 块每秒，32/64/128 分别约 822/737/645。完整文档流程在两组数据上均以 16 最快。增大内部批次会增加 padding 与显存占用。

在 256 篇短文档的单槽完整清洗中，6.77 秒里 `_forward` 累计 6.03 秒（442 次），编码 0.28 秒、解码 0.10 秒；64 篇混合文档的 11.75 秒里 `_forward` 累计 10.48 秒（641 次），编码 0.56 秒、解码 0.20 秒。当前主要瓶颈是大量小批次前向。队列完整路径在模型已预热后，短文档 256 篇用 7.51 秒（2,046 篇/分钟），混合文档 64 篇用 11.97 秒（321 篇/分钟）；报告、进度和队列读写并未吞掉大部分时间。

## 调度方案对照

下表是独立实验脚本对完整单条清洗入口的测量，包含分块、模型推理和临时报告写入。`GPU 峰值分配`仅是该实验进程的 PyTorch 峰值，不含清洗台等其他进程。

| 方案 | 短文档 256 篇/分钟 | 混合文档 64 篇/分钟 | 结果差异 | 观察 |
| --- | ---: | ---: | ---: | --- |
| 原流程，1 实例、1 文档槽、内部批 16 | 2,252 | 327 | 基线 | 模型调用约占总时长 98% |
| 原流程，1 实例、4 文档槽、共用推理锁 | 2,475 | 329 | 0 | 短文档小幅提升，单篇等待增加 |
| 2 份模型、2 文档槽 | 2,588 | 333 | 0 | 短文档略快，但双份权重增加显存与 CPU 开销 |
| 1 份模型、2 文档槽、直接并发调用 | 2,628 | 336 | 0 | 高槽位进一步退步；并发模型调用仍需长期正确性验证 |
| 1 份模型、4 文档槽、短请求合并、内部批 16 | **3,051** | **341** | **0/256、0/64** | 约 2 毫秒收集窗；短文档快约 35%，混合文档快约 4% |
| 同上，8 文档槽 | 3,097 | 341 | 0 | 吞吐提升很小，长文档 P95 等待明显增加 |

短请求合并方案仍只有一份模型和一条 GPU 推理执行流，将同时到达的片段送进同一次 `predict_batch`，再按输入顺序分配结果。4 槽短文档实测模型调用从 274 次降到 82 次，实验进程 GPU 峰值分配约 1.67 GB；8 槽和更大内部批没有足够收益。64 篇混合文档的 4 槽方案 P95 单篇延迟约 1.50 秒，原单槽约 0.44 秒，说明批量吞吐的收益伴随等待时间增加。

## 临时队列端到端验证

先在 `/tmp` 建立包含同一批 256 篇短文档的临时清洗项目，用原 `clean_queue` 写进度、清洗 JSONL 和报告；实验调度由临时包装器接入。模型预热后，原调度 7.88 秒、单模型合并调度 5.35 秒；两边 256 篇的最终决定和清洗正文完全相同。实验队列暂停在约 83 篇后续跑至 256 篇，报告也一致。

随后将合批器接入正式 `LayaCleaner` 和 `clean_queue`，仍只在 `/tmp` 临时队列跑实际生产代码，正式队列没有启动。同一批 256 篇，单槽基线 **7.03 秒**（约 2,185 篇/分钟），新调度 **5.49 秒**（约 2,798 篇/分钟），约快 **28%**。两边各 256 篇报告的决定和正文逐篇一致，最终都是保留 255 篇、删除 1 篇。新调度暂停于已处理 20 篇，重新启动并续跑至 256 篇；最终报告仍与单槽基线全部一致。这个速度主要针对样本中的短文档，不能直接外推到整个维基队列。

## 结论与代码接入

进一步在相同样本上调收集窗：0 毫秒基本不合并；1～2 毫秒有收益，5 毫秒没有额外收益。4 文档槽、收集目标 128 块、2 毫秒窗时，短文档约 3,045 篇/分钟，混合文档约 349 篇/分钟，结果仍逐条一致；目标 64 块约 2,998 和 347，差距很小。优先选择**一份权重、4 个文档槽、短请求最多等待 2 毫秒后合并至约 128 块、模型内部批 16**。不要通过复制模型实例来追求并行数。这套调度现已接入 `dataset/label/backend/laya_cleaning.py` 的 `LayaBatcher` 和 `dataset/label/backend/batch_clean.py` 的 Laya 专用四槽位。合批器只在批量运行期间存在，单条人工清洗继续使用原入口，并与合批器共享模型推理锁。模型的判断问题、切块、报告格式、缓存身份、队列进度和其他模型来源的调用方式均保持原样。已通过标注工具全部 153 项后端测试、实际 Laya 临时队列对照和暂停续跑验证。正式队列保持暂停，`processed=9236`、`last_ordinal=16224` 未修改。
