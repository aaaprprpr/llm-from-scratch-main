# 2026-09-23 远端预训练 40k 步复核

> 历史记录（2026-10-05 整理）：本报告只描述 `run_20260922_103413` 的优化失稳迹象；它不是旧版 103,510 步 AdamW 模型的数据对照。文中的进程、配置和建议是当时状态。此前过强的因果表述已收窄；后续数据与模型对比见 [MiniMind 完整版评测](2026-09-23-MiniMind完整版预训练评测.md)。

## 结论

**退化在 40k 步没有恢复，也没有继续恶化，而是稳定停在一个远差于起点的平台上。** 40k 的 val loss=4.9097，低于 20k 的 5.0500，但仍比 5k 的 3.7172 差了 1.19 nats。本次最佳 checkpoint 是 5k。

**这个 Muon run 出现了明显的优化失稳迹象。** 各语言窗口的 loss 都恶化，部分矩阵权重、残差和梯度持续增长，因此需要检查优化设置。但下面是同一 run 的观察性统计，没有只改变优化器的对照训练，不能唯一定位根因，也不能排除数据与优化设置的相互作用。旧版 AdamW 权重与 MiniMind 的数据对比属于另一组实验。

本次检查全程只读：复制了 checkpoint、日志和 CSV 到本机评估，没有中断远端进程（PID 373949 仍在运行，100% GPU、287W），没有修改远端任何代码、配置、数据或 checkpoint。

## 2. 生成质量：40k 明显差于 5k

同一组提示、temperature=0.3、固定种子：

```text
5k    输入：因为外面下着很大的雨，所以我
      续写：,那就是"我们现在做到的,现在我们搞了,现在我们搞了……   （复读，但语法通）

40k   输入：因为外面下着很大的雨，所以我
      续写：,那就是在外面,它可以避免在在的,因为了.如果没有一个例子,
            那么就会不能把我的身上……                        （语法破碎）

5k    输入：小明把红色钥匙放进左边抽屉……红色钥匙原来在
      续写：红河中,马上返回直边,然后又返回住红河中,红河边区边区边区……（复读但有实体）

40k   输入：小明把红色钥匙放进左边抽屉……红色钥匙原来在
      续写：红花花花,把红花花,把红花,把红花红花,把红花红花红花木红花……（字符级崩塌）

40k   输入：你好，我是
      续写：!<|endoftext|>                                    （第二个 token 就吐 EOS）
```

40k 出现 5k 没有的失效模式：直接复述提示词、字符级循环、以及问候语触发 EOS。5k 的复读是"黏在模板上"，40k 是"结构本身散架"。

## 3. 逐语言窗口观察：各组都出现退化

把 32 个固定验证窗口按中文占比（汉字/字母字符）排序，比较 5k 与 40k 的逐窗口 loss：

| 分组 | 窗口数 | 5k loss | 40k loss | 平均变化 | 变化倍数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 低中文 <50% | 7 | 2.1507 | 2.8544 | +0.7037 | **×1.327** |
| 混合 50–80% | 1 | 3.5031 | 4.4870 | +0.9839 | ×1.281 |
| 中文为主 ≥80% | 24 | 4.1830 | 5.5267 | +1.3437 | **×1.321** |

**32 / 32 个窗口全部恶化**，包括 7 个纯英文窗口。三个语言分组的变化倍数几乎相同（1.28～1.33）。

各组同步恶化，说明此次退化并不只出现在中文验证窗口。这能提示全局训练问题；但数据引起的参数变化也可能同时影响不同语言，不能据此否证数据问题。

分组间绝对变化也不能直接比较：这些英文窗口在 5k 时 loss 本来更低。中文占比与绝对退化幅度的 Pearson r=+0.806，只是这 32 个窗口的相关性，不能作为根因判断。

## 4. 参数分组观察：Muon 矩阵权重持续增长

同一次训练中，不同模块分别使用 Muon 或 AdamW。它们的结构、梯度路径和功能也不同，所以这不是“只有优化器不同”的受控实验：

| 参数组 | 优化器 | weight_decay | 5k→40k 权重 RMS 变化 |
| --- | --- | ---: | ---: |
| attn out_proj | Muon | **0.0** | **×3.952** |
| attn qkv_proj | Muon | **0.0** | **×3.063** |
| ffn w2 | Muon | **0.0** | **×2.939** |
| ffn w1 / w3 | Muon | **0.0** | **×2.886** |
| RMSNorm gain | AdamW | 0.0（norm 不衰减） | ×1.027 |
| embedding | AdamW | 0.1 | **×0.690** |

**带 weight decay 的 embedding 在收缩，而无衰减 Muon 矩阵组（47,775,744 参数，占模型 77%）增长约 3～4 倍。** 这个现象支持进一步检查 Muon 的学习率与衰减设置；它本身不证明权重衰减就是唯一原因。

配置确认：`configs/pretrain.json` 中 `optimizer.weight_decay=0.1` 只作用于 AdamW 组；`optimizer.muon.weight_decay=0.0`，而 Muon 组持有 77% 的参数（`train/pretrain/run_train_model.py`）。

## 6. 同期发现的数据集问题

数据集的问题上一轮已经查实，本次没有推翻：

- 11 个来源中只启用了 `fineweb_edu_zh_4_5` 一个（`configs/data_pipeline.json:299-345`）。
- 4,096 篇完整文档抽样中，中文比例 <20% 的占 15.1% 文档、**26.28% tokens**，全部来自 `IndustryCorpus2`（该来源占 38.22% tokens，其中 57% 文档是低中文）。
- 存在超长英文医学/生物论文（最长 63,921 tokens），携带引用、表格和 LaTeX。
- 现有清洗 17,790,513 条只过滤 748 条（0.0042%），未覆盖语言、篇内重复和网页模板。

**这些分布问题与中文日常表达目标不匹配，值得处理。** 固定验证集的 loss 回升，同时出现权重和梯度增长，需要将数据问题与优化问题分别验证；本报告没有完成能够区分两者的单变量实验。

这些观察应作为候选解释，而不是承诺换数据或某个优化参数必然修复训练。

## 7. 当时的建议（不是现行待办）

1. **停掉当前 run。** 40k 相对 5k 没有任何一处更好，已连续 28k 步停在劣质平台，继续跑到 228k 只是消耗 GPU。保留 5k 和 30k/40k 文件做对照。本次没有替你停，进程仍在跑。
2. **先做优化器对照，再谈重训。** 上一轮报告（`docs/历史记录/2026-09-22-Muon预训练退化审查.md`）建议的全 AdamW 基线至今没有跑。同结构、同词表、同数据顺序、同验证窗口，LR=3e-4、betas=(0.9,0.95)、矩阵 weight_decay=0.1、norm 不衰减、梯度裁剪=1。观察点必须越过 4.5k～5k 这个退化起点，不能再看单步成功。
3. **若继续研究 Muon，可尝试非零 weight decay**（例如 0.1），并把 `muon.max_lr` 从 0.02 降到 0.003～0.005。这两个是待验证的起点，不是已证明的结论；一次只改一个变量。QK normalization 是候选但属架构改动，要单独验证。
4. **恢复 5k 时要小心优化器状态。** `load_state_dict` 会带回旧优化器的 param groups，只改 JSON 里的 `weight_decay` 再普通 resume 会被 checkpoint 里的 0.0 覆盖，需要显式覆盖恢复后的参数组，或只加载模型权重重建优化器。
5. **稳定性确认后再重建数据。** 按上一轮 `docs/历史记录/2026-09-22-FineWeb中文语料清洗审查.md` 的建议做中文语言过滤（主池 ≥70%）、篇内重复清理和来源 token 配额，重点削 `IndustryCorpus2` 的长英文文献。写入新路径 `train_zh_v2.bin`，不要在训练中替换同名文件。词表保持 24,576。
6. **短期提 checkpoint 频率。** 最优点落在 4.5k 而 checkpoint 在 5k 间隔上，好模型直接丢了。既然退化发生在 5k 附近，间隔应临时调到 500～1000 步。
