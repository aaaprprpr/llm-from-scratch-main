# 单篇语料清洗调用链与调整记录（2026-09-28）

> 历史记录（2026-10-05 整理）：本文件汇总 9 月 28 日的调用链、样例修订和提示词迭代，不再作为现行操作指南。模型默认值、来源调度、解析和服务启动行为已有后续变化；文中的“当前”“现在”均指记录当时。现行使用说明统一放在 [语料清洗台说明](../操作参考/语料清洗台.md)。后续已采用 v16 提示词、单请求 30 万字符/单篇 100 万字符、Qwen 按需加载和批量多来源调度；以下旧参数与旧默认行为只用于追溯。

记录日期：2026-09-27。本文对应网页上的“自动清洗并保存本条”，不是命令行批量入口。

## 从点击到看到结果

1. [DocumentWorkspace](../../dataset/label/frontend/src/components/DocumentWorkspace.tsx) 调用 `cleanCurrentDocument`。[useReviewWorkspace](../../dataset/label/frontend/src/hooks/useReviewWorkspace.ts) 把当前可编辑段落序列化，带上队列、序号、来源哈希和审核修订号，向 `POST /api/reviews/documents/{doc_id}/llm-clean` 发请求。按钮变成忙碌状态；此请求直到整篇处理完成才返回。
2. [reviews.py](../../dataset/label/backend/routes/reviews.py) 从队列读取文档，核对文档 ID、来源哈希和修订号，然后**先关闭数据库连接**，再调用 `context.llm_cleaner.clean(...)`。长时间的模型推理没有占着数据库事务。
3. [llm_cleaning.py](../../dataset/label/backend/llm_cleaning.py) 检查输入长度、段落 ID，按输入、模型、提示词内容指纹和分块设置查本地 JSON 报告缓存；命中已完成且提示词一致的结果时，不调用模型。未命中时，进程内的锁保证一次只跑一个文档清洗任务。
4. `split_units` 把段落按换行及中文句末标点切成片段，单片段最多 1200 字符，并保存原段落 ID 和字符偏移。`_plan` 尽量保持原审核段落完整，按配置的片段数、字符数和上下文预算组块。当前 DeepSeek 配置最多 4096 片段、100000 字符，900000 上下文、32768 输出 token；放得下时整条只组成一块。规划上下文采用保守的 UTF-8 字节估算。以前的远端配置是每块 48 片段、3000 字符、32768 上下文、4096 输出 token。
5. `_clean` 对远端模型在确需分块时**最多同时处理 4 块**，收齐结果后仍按原文块序组装。每块把系统指令、JSON Schema、标题和编号片段放入消息，经 `_request` 发送到所选服务的 `/chat/completions`，等待完整 JSON 响应。当前配置是 DeepSeek `deepseek-flash`、关闭思考、`stream: false`，单个 HTTP 请求超时 300 秒。本地模型默认保持 1 路。
6. 返回后用 Pydantic 解析，并核对删除编号、编辑是否只删原文字符、拼接是否保持顺序。当前 DeepSeek 配置每块最多请求一次，避免长文格式错误时自动再次付费；其他配置默认最多两次。多块文档有失败块时保留该块原文，完成块写入报告供续跑。已有报告里的成功分块可复用，未完成分块再试。
7. 所有块结束后，将保留的文字、删除和局部修订拼接成最终正文，写入 `dataset/label/data/llm_suggestions/cache/` 下的分片 JSON 报告。模型按片段的语义作用区分连贯正文与页面组织碎片；组装阶段仅核对编号、顺序与原文裁剪是否合法，不按关键词强制补删。
8. 路由仅在所有分块完成时调用 `set_document_review`，直接保存决策和清洗后正文；若有未完成分块则返回 `saved: false`，不覆盖现有审核。前端收到 `saved: true` 后再 `GET` 当前文档，刷新编辑器；右栏的差异由浏览器 Worker 计算。

| 旧版文档记录（24 片段、串行） | 分块 | 模型重试块 | 输入 / 输出 token | `_clean` 耗时 |
| --- | ---: | ---: | ---: | ---: |
| 第 3 条《文学》 | 8 | 0 | 18,945 / 3,487 | 79.82 秒 |
| 第 2 条《哲学》的早期记录 | 23 | 6 | 74,383 / 14,067 | 561.52 秒 |

数据取自本地 `llm_suggestions` 报告。耗时是服务端 `_clean` 的总墙钟时间，不含浏览器刷新、数据库最终写入；系统目前没有记录每个 HTTP 请求的耗时，所以不能精确拆出网络、排队和模型生成各占多少。

**旧版主要耗时是多次串行的远端模型调用。** 第 3 条等待了 8 次完整响应，平均每块约 10 秒；第 2 条有 23 块和 6 个重试块，约 29 次请求。每块又重复发送较长的规则和 Schema。虽然模型上下文配置为 32768，24 片段的固定上限仍使长文拆出很多块。缓存命中、分句、拼接、JSON 写盘和前端 diff 不是这两个记录所显示的主要耗时来源。

## 与第三条标题漏删的关系

第三条原始分块中，`诗歌 `本来就是独立段落；`文学技巧 \n`被 `split_units` 单独切出，后一句解释是另一个片段。此前模型漏删，后续加过按短中文词匹配的确定性补删规则。该规则只覆盖少量标题，不能正确处理日期或书目，现已删除；模型统一判断所有片段。历史上已保存的第三条人工修订保持原样。

## 本次提速与验证范围

- 远端模型每块上限从 24 调到 48 片段，输出 schema 的删除/修订条目上限同步调整。按旧输入离线重新规划，第 3 条由 8 块变 4 块，第 2 条由 23 块变 12 块；片段本身的切分和保留顺序不变。
- 远端模型最多 4 块并发，完成后按原文顺序组装。每块的耗时、请求次数、片段数和 token 用量写入新报告的 `result.chunk_timings`。本地模型默认串行。
- 4 块各模拟 120ms 等待的本地测试中，串行为 0.487 秒、4 路并发为 0.128 秒，输出正文相同。这是执行机制测试，**不是远端 API 加速实测**。真实数据重发到 DashScope 的计时被自动审批拦截；未绕过审批，不能给出真实加速倍数。实际耗时还取决于接口并发限制、排队、输出长度和重试情况。
- 现有已保存的审核正文保持原样；新分块方案使用新的提示词/缓存版本。若要比较新旧清洗质量，需要在获得允许后对同一批原文做实测，重点看正文误删、漏删和未完成块。

## 更换模型后的速度对照

当前 `configs/label.json` 选用 DeepSeek `deepseek-flash`，密钥来自项目根目录 `.env`。Claude 插件使用的是 DeepSeek Anthropic 兼容地址；此清洗器使用 OpenAI 格式，因此连接的是 DeepSeek 官方 `https://api.deepseek.com/chat/completions`，并在请求中设置 `thinking: {"type": "disabled"}`。

用程序生成的相同 24 段中文测试文本，分别调用一次现有 Qwen Plus 和 DeepSeek Flash。两次均为 1 个分块、1 次请求，且返回完整的清洗结果：

| 模型 | 完整调用耗时 | 输入 token | 输出 token |
| --- | ---: | ---: | ---: |
| Qwen Plus | 15.51 秒 | 3,239 | 678 |
| DeepSeek Flash | 1.95 秒 | 3,103 | 484 |

这只是单次、合成文本的接口延迟对照；输出 token 数不同，真实维基长文的耗时和清洗质量仍需按实际任务观察。历史记录中的 79.82 秒和 561.52 秒属于旧版分块配置，不能直接视作这次模型切换后的预期耗时。

此外，网页读取当前文档时曾同步初始化 tokenizer 并计算未在页面展示的 token 统计；本地冷启动剖析约花 1.9 秒，已移除。此项优化影响打开文档的速度，不影响上述模型请求耗时。

## 与自动清洗队列的进度关系（2026-09-28 更新）

单条按钮完成后，正文和决策保存在 SQLite 的 `document_reviews`，`actor=llm-clean`；批量任务的逐条结果写入 `batch_cleaned/.../progress.jsonl` 和 `cleaned.jsonl`。两者是同一队列的两种入口，进度接口现在按队列序号合并并去重：单条 LLM 保存数单列显示，若它已被批量扫描，总完成数只算一次。仅保存为 `unsure` 的记录不算清洗完成。

批量任务对尚未扫描的条目读取最新人工决策；明确保留或丢弃的条目直接采用人工结果。尚未确认的条目与网页单条按钮调用同一个 `LlmCleaner.clean()`、同一提示词和同一完成判定。批量只增加工作池、持久进度和续跑；现在每篇只发起一次完整 `clean()` 调用，不再额外连续重洗三遍。模型内部对无效分块的重试规则仍相同。已经批量处理过的条目如随后被人工确认修改，批量原始日志仍保持追加记录；「生成合并语料」会用最新人工正文覆盖对应的批量结果，输出 `effective_cleaned.jsonl`。人工或批量进度有更新时，页面会提示旧合并文件需要重新生成。全量批量任务正常结束时会自动生成一次。

清洗页按原队列序号读取批量结果：已保留的正文直接进入编辑器与右侧差异预览；整条丢弃的段落显示为已删除，可逐段恢复；未完成的条目保留原文待核查。人工确认结果优先于批量结果。当前打开的条目在后台刚处理完成且用户没有未保存的正文或标签时会刷新显示；无需重新调用模型。待定审核不计作完成。

「暂停」会先停止向工作池提交新文档，再等待已在执行的文档结束当前 `clean()` 调用并把结果写入进度日志。它不会取消正在等待的远端 HTTP 请求，因此长文仍可能等到当前请求结束或达到超时，随后状态才从「暂停中」变为「已暂停」。暂停不影响网页单条清洗。

## 2026-09-28 独立日期与书目漏删复查

《2003年7月》的旧报告中，`7月31日` 等已按单换行分为独立 unit，前 3 个分块仍有 25 个日期被模型保留；旧短标题规则限定纯汉字，因此也未删除日期。《孙中山》的旧报告里，书籍、论文、译著列表被模型保留，`文集` 段落恰好跨两个分块，前后判断不一致。问题不是只按双换行拆分，而是模型说明不够具体、旧短标题规则掩盖了漏判，以及固定 48 片段分块会割裂同一个段落。

当前判据按片段表达的语义逐条判断：保留能读懂的事实、过程与解释，短句和列表中的事实也保留；删除仅作分组、检索或登记的残片。第 50 条《诺贝尔奖》证明旧提示词把整栏的获奖事实误标为 `link_list`，反复清洗还会累积误删；因此现在明确保留主体与事件、成果或关系的对应陈述，即使语法简短或同栏成排。与之相对，单独的名称后只附括号状态、没有形成叙述的行须删除。切分与组装不执行按词、日期、奖项或设施名称的删除规则，是否列入 `removals` 仍由模型逐片段决定。提示词内容哈希隔离旧报告，已保存的旧审核正文不会因修改提示词自动重写。

真实完整原文验证：《2003年7月》5 块、无失败，独立日期行全部删除，事件正文保留；《孙中山》18 块、无失败，作品名单及纯片名加年份、时长、机构的条目删除，作品内容论述保留。另用未参与提示词编写的坐标、人名串列、专利号、无句号短陈述和诗句验证了同一判据。两篇结果已作为可撤销的审核修订写回；批量队列不自动重洗其他历史结果，每条新增进度记录带 `prompt_sha256`。模型仍可能漏判，单次样本通过不代表整个语料零错误。

## 2026-09-28 第 56 条长文与调用次数

第 56 条输入 50,452 字、273 段，内部拆为 1,279 个保留原文偏移的 `unit`。旧配置按 3000 字和 48 `unit` 的上限分成 30 块，因此实际调用 DeepSeek 30 次（输入合计 110,455 token、输出 2,743 token），第 28 块被接口以 `Content Exists Risk` 拒绝。这里的 `unit` 只是模型输出删除位置的编号，不再意味着每个 `unit` 单独调用 API。

当前配置将这条规划为 **1 块、1 次请求**，请求正文约 250 KB。一次真实调用仍被 DeepSeek 以相同的 `Content Exists Risk` 拒绝，说明增加上下文不能消除接口对这条内容的拒绝；这次单次调用没有写入审核。前端清洗结果现在显示本次模型请求次数与条内分块数。超过配置上下文或片段上限的极端文档仍可拆块，不会截断输入。

## 2026-09-28 备用模型与逐条状态

DeepSeek 返回明确的 `Content Exists Risk` 时，同一 `LlmCleaner` 只对被拒的块改用配置中的 Qwen Plus 请求一次；成功结果照常校验、拼接并缓存，报告记录实际模型和两次请求。Qwen 也失败则保留原稿，批量进度记录为待人工处理，不再换模型重试。第 56 条已直接用 Qwen 单次验证，同样收到 HTTP 400（`Input data may contain inappropriate content`），没有写入人工审核。

清洗页侧栏按队列序号分页查询 `progress_index.sqlite3`、当前人工审核及 SQLite 中的单条 AI 失败记录，显示未清理、人工清理、单条 AI、批量清理、明确敏感拒绝、历史接口拒绝、其他失败和待复核。网页单条清洗失败也会留下状态；成功保存审核时清除该失败记录。历史批量日志只有 HTTP 400 而没有接口详情时，显示“接口拒绝待人工”，不擅自断定为敏感。提示词升级继续使用同一队列与模型的既有批量进度目录，因此旧进度不会归零；新处理记录使用新提示词和缓存指纹。

针对两个真实片段做了小样本验证：第 50 条的获奖事实保留，《亳州市》的孤立“名称＋括注状态”删除。随后用第 50 条的简体原文完整清洗一次，模型保留了截图中居里家族及其他获奖事实；该整篇结果仍夹有此前已删的表格说明，因此没有整篇覆盖当前草稿。只从已核对的原文结果中恢复两组误删事实共 857 字，按审核版本 4 写入版本 5，原有其余删除保留。短片段和单篇验证都不能保证整个语料零误判。

## 2026-09-28 第 98 条 TeX 占位样例

第 98 条《TeX》的旧报告已经把 LaTeX 模板、编译命令切成独立段落；问题不在双换行切分。旧提示词把它们当成代码示例保留，新提示词 v10 对已清洗的全文发了 1 次请求、返回 0 处删除，摘要也明确说保留代码示例。此前“完整代码可保留”的准则没有区分有实质内容的代码与只展示待填写位置的样板。

v11 改为按实际内容判断：占位模板和孤立的命令演示不因使用代码语法就自动保留；删除示例时也清除依附它的引导、续句。第 98 条当前审核从版本 1 更新到版本 2，只删除这些片段及残句，共 237 字，保留前后的 TeX 说明。一次外部 DeepSeek 全文验证被自动审批拒绝，因此 v11 对其他文档的实际模型效果仍需后续观察。

## 2026-09-28 第 135 条短行名单漏删

第 135 条《美国》的 v11 报告使用 1 个整篇请求，输入 45,329 token、输出 260 token；846 个原文 unit 中，模型只建议删 12 个栏目标题。宗教比例原本逐行切分，行政部门段落的前五行是解释、后十行只有部门名，另一个机构段落夹有三个裸名称。模型看到了这些独立 unit，却把整段当成正文留下，属于长文中语义判定过粗，并非双换行导致无法删除。

v12 在同一次请求里额外重列成组的短行及原 unit 编号，提醒模型逐条复核；这只改变关注位置，不按字数、百分号或机构名称执行自动删除。第 135 条本地检查选出 40 个待复核 unit，仍规划为 1 次请求。当前已保存审核按版本 1 更新到版本 2，删去宗教比例单元格、两处机构裸名单，共 147 字；相邻的部门职责和其他事实句保留。v14 小样本经 DeepSeek 和本地 27B 验证：两者都删除了这组裸名单与比例，同时保留前面的部门事实句；整篇长文仍可能漏判。

## 2026-09-28 第 179 条年表与模型来源设置

第 179 条《元明清历史年表》的旧审核保留了逐年事件记录。用户确认只保留首句导言；当前正式审核已从版本 1 修订到版本 2，正文为“元明清历史年表为元明清三朝的历史年表。”。v14 提示词按整体表达形式区分逐年检索记录和可连续阅读的历史叙述，并明确年表前的独立导言应保留。它不按年份关键词硬删。DeepSeek 对导言加第一段年表的 1,140 字样本最终删除 65 个年表片段、只保留首句。本地 27B 在较短输入上也做到这一点，但旧版对 7,781 字全文曾留下 5,173 字年表，不能将短样本结论扩大到整篇。

DeepSeek 曾回显输入里的 `review_focus` 字段，导致严格 JSON Schema 解析失败。当前解析只忽略这个输入辅助字段，其余未知字段仍拒绝；v14 提示词也明确禁止回显。六次外部小样本请求仅在用户明确同意第 179、50、135 条原文外发后进行，报告见 [本地 Qwen 27B 清洗试验](2026-09-28-本地千问清洗试验.md)。

清洗台“设置”分别保存单条清洗与批量清洗的模型来源。默认单条 DeepSeek、批量本地 27B；Qwen API 可分别选择。批量切换模型后沿用原队列进度，实际模型逐条写入记录。清洗台启动时自动检测同级 `qwen/` 模型服务，未启动则加载；本地请求等待服务就绪。
