# Laya TileLang 加速验证（2026-09-30）

本次只读取已抽样的维基正文，在 `/tmp` 建临时队列；没有调用付费 API，也没有启动正式清洗队列。硬件为 RTX 5070 Ti，模型为 `laya_wiki_cleaning_v1`。启动后优先调用 Laya 自带的 `accelerate(strict=False)`；编译环境不可用时自动使用原 PyTorch 前向。单条和批量清洗共用这一个模型实例。模型内部批大小维持 16；在 8192 个真实片段上，增到 32 后运行明显变慢，64 触发显存不足。

快速前向与原前向在 8192 个片段上有 3 个处于约 0.50～0.53 置信度的判断差异。因此对快速结果中置信度低于 0.55 的批次，用原前向按**相同输入批次**重算，再取这些边界片段的原前向答案。只拿不确定片段单独重算会改变 padding 形状，使其判断在 0.5 附近再次翻转。

| 临时队列 | 原前向 | 快速前向完成预热后 | 最终正文差异 |
| --- | ---: | ---: | ---: |
| 256 篇短文档 | 5.47 秒 | 5.10～5.22 秒 | 0/256 |
| 64 篇混合长度文档 | 11.03 秒 | 9.81 秒 | 0/64 |

首次快速运行需要编译新形状，可能比原版慢；在这两组样本上首次分别约 6.70 秒和 14.73 秒。单独的大批片段前向约快 1.4 倍，但完整队列还包含分块、组装、报告和边界复核，因此实际增益较小。不能把这些样本速度直接外推到全量语料。

初次基准使用系统 Conda Python 加 `/tmp` 临时依赖。重启后项目 `.venv` 可正常导入并运行 TileLang，但正式队列在新输入形状上触发 NVCC 编译，因缺少 `cuda_runtime.h` 连续失败。现已在 `.venv` 安装与 NVCC 13.4 匹配的 `nvidia-cuda-runtime==13.4.92`；用原失败的四篇文档共 83 个片段复测，快速内核成功。Laya 适配层另增加运行时回退：若以后某个新形状的快速内核失败，本批次改用原 PyTorch 前向，避免整个批量来源被连续编译错误停用。正式队列没有在本次修复中启动。
